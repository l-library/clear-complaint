# 每日健康关怀（Daily Companion）实施计划

状态：**规划中，未实施**。本文件是 `feat/daily-companion` 的骨架与排期依据；
落地前每一步先回来更新这里的验收栏。平台契约以交接文档 16.8 为准
（私有目录 `Documents/private/clear-complaint/`，密钥不入库）。

## 1. 想法与边界

用户戴着（先模拟的）手表过完一天。后端把当天手表数据与本人授权档案
（问诊记录、病历、已确认的照护安排）交给 Daily-Health-Companion 工作流，
产出一份当日小结：肯定用户做了什么、温和提醒该注意什么，重点是情绪价值，
而不是一份新的诊断或健康评分。

想法原文：「模拟一个手表数据，交给大模型，模型能调取他所有的档案，
包括问诊的健康档案和病例的健康档案，根据这一天手表的数据给一个每日总结。
主要是情绪价值上，比如你做了什么事情对你的病会有利，什么事情不要做对你的病有害。」

与想法的两处偏差，原因写在这里，免得后面反复：

- 「做什么对病有利/有害」不能由模型凭常识编。工作流只允许引用档案里
  `confirmed: true` 的照护安排（care_guidance），并逐条带 `record_id/
  condition_id` 回溯。「有害」这半句在 v1 表达为「不因设备分数自行加量」
  式的温和提醒，不做负面清单。这符合本仓库非协商约束：模型输出不直接
  变成面向用户的结论。
- 「调取所有档案」在后端完成。前端不传任何档案字段，也不传手表原始数据；
  档案由后端按登录身份检索整理（16.8.8 第 1、3 条）。

## 2. 已验证事实（2026-11-24 首测，2026-11-27 复核）

凭据与 URL 来自《鉴权信息-仅后端(2).md》。这是该 Key 首次通过 HTTP 验证，
文档 16.8.1 的「发布 URL 未验证」可以销项。

| 用例 | 结果 |
| --- | --- |
| 简版（5 指标 + 高血压档案 + 步数目标） | `ready`，协议五项回显校验全过，connection/tomorrow 均只引用已确认安排 |
| 无档案 | `ready`，`used_record_ids: []`，不编造建议 |
| 待核实标记（review） | `review_required`，`model_selection_applied: false`，跳过模型 |

| 缺 `schema_version` | `invalid_input` / `INVALID_REQUEST`，`request_id` 正常回显（2026-11-27 复核；旧稿记「不回显」，已不成立） |

| 带 `baseline`（2026-11-27 新增） | `ready`，同设备同口径，步数／睡眠／静息心率三项 7 天观察差值 |
| 两条已确认照护安排（2026-11-27 新增） | `ready`，步数与睡眠各一条联系、各一条明日安排 |

每次调用 HTTP 200、SSE 终态 `succeeded`；`workflow_version` 在 2026-11-27 的 12 次
调用中均为 `2026-11-24.daily-companion.2`（2026-11-24 交接稿记 `.1`，平台随后升到
`.2`）。响应 `schema_version` 仍是 `clear-complaint.daily-companion.workflow.v1`，
没有 `.v2` 响应 schema：文档里说的「v2」指 DSL 版本 `.2`，不能按 `.workflow.v2` 去
校验。顶层九字段白名单强校验在升版后仍成立，多出的 `user_memory` 等键返回
`invalid_input / INVALID_REQUEST`，验收用例行为不变。

平台侧曾有毛病（与本仓库无关，曾列入给平台协作者的清单）：schema 校验失败时
request_id 回显为空串，客户端按「请求关联不匹配」处理会吞掉真实错误原因。
2026-11-27 复核时不再复现：缺 `schema_version`、顶层多出 `user_memory`、
`schema_version` 取值错误三类失败都逐字回显 `request_id`。所以不要为它实现
「回显为空即判关联失败」的旁路；`request_id` 缺失只记日志，错误以 `error_code`
为准。畸形 JSON 是否仍回显空串没有测，后端保留空值分支（api-agentarts.md 16.3.2）。
triage 当年报过同一现象，本次未复测，不能据此认定 triage 仍有此问题。

2026-11-27 复核：运行时 `agent-arts-fe15b614a68241f0b850005b9b325630`，12 次全合成
调用均 HTTP 200、`content-type: text/event-stream`，终态 `succeeded`，耗时
0.5–20.6 秒，在 16.8 的 60 秒预算内；响应顶层恰好 16 个键，没有出现五种之外的
status。与交接稿不一致的三处已按实测写回 api-agentarts.md 16.8.6 / 16.8.7：版本是
`.2`；校验失败回显 `request_id`；失败路径的 `data_source` 为 `unknown`、`report_date`
为 `""`、`summary` 为 `null`、`data_quality` 为 `{}`。`data_quality.coverage_limited`
在 `available_metric_ids` 为空时仍为 `false`，判空要用 `status` 或
`available_metric_ids`。`degraded`（模型输出被拒）、认证失败、SSE 断流本轮没有覆盖。

证据在仓库外：`Documents/private/clear-complaint/daily-companion-实测-2026-11-27.md`，
探针脚本在 `Documents/private/clear-complaint/daily-probe-harness/`，都不入库。
以上只证明平台契约可用；`app/daily`、迁移与前端展示页随后已按 D1–D4 落地（见第 5 节）。

## 3. 架构骨架

按仓库约定落位，不引入新目录形态：

```
backend/
├── app/core/config.py          Settings 增加两条：agentarts_daily_companion_url / _api_key
├── app/agent/client.py         workflow 映射表增加 daily：请求/响应 schema、超时 60s
├── app/daily/                  新领域包（router / service / schema / models）
│   ├── mock_watch.py           合成手表数据生成器，data_source=mock，绝不读真实患者数据
│   ├── archive.py              档案摘要组装：profile + episode 摘要 → consultations
│   ├── models.py              daily_report 表
│   └── ...
└── alembic/versions/0007_*    daily_report 迁移
frontend/src/pages/daily/       展示页 QDailyReport（D4 已落地，接口契约仍以 docs/api.md 16 为准）
```

- 表 `daily_report`（单数命名）：`BIGINT GENERATED BY DEFAULT AS IDENTITY` 主键，
  `user_id` 外键，`report_date`、`workflow_version`、`data_source`、内部
  `status`、`summary`（JSON）、`data_quality`（JSON）、`used_record_ids`（JSON）、
  输入快照哈希、`created_at/updated_at`。唯一约束 `(user_id, report_date,
  workflow_version)`：一个用户一天一份当前报告，重复生成按更新覆盖，
  迟到旧结果不覆盖新报告（16.8.8 第 6 条）。
- `workflow_version` 存平台回显值，不在客户端写死断言：平台每次发布新 DSL 都会 bump
  （交接时 `.1`，2026-11-27 已 `.2`），写死会让下一次发布时所有生成失败。
- 响应解析要能接受 `invalid_input` 的空壳：`summary` 为 `null`、`data_quality` 为
  `{}`、`report_date` 为 `""`、`data_source` 为 `unknown`（api-agentarts.md 16.8.7 末）。
- 不做：user_memory、逐秒采样、ECG 波形、通用健康评分、推送。工作流本版
  就没有这些入口，文档明说不假装支持。

## 4. 档案输入的现状（关键短板，先说清）

v1 能组装出的档案是薄的：

| 16.8.4 字段 | v1 来源 | 现状 |
| --- | --- | --- |
| `profile` | 账户档案 | 可用（preferred_name/age/sex） |
| `consultations` | episode 列表摘要 | 可用（已有问诊记录） |
| `confirmed_conditions` | 无来源 | 病历导入尚无后端接口，episode 的「可能相关情况」按契约不得转确诊，恒为 `[]` |
| `medical_records` | 无来源 | 恒为 `[]`，等病历导入功能 |
| `care_guidance` | 无来源 | 无「已确认照护安排」实体，恒为 `[]` |

无档案用例已实测可用，薄档案只会少生成「与个人照护目标的联系」板块，
不会出错。**这意味着情绪价值的核心闭环（肯定 + 温和提醒）在 v1 就能走通，
「联系疾病」板块要等病历导入和照护安排实体落地后才长出来。** 这是排序的
主要依据，也是要向提出想法的人明说的预期差。

### D3 的接口草案（定契约用，实现前可改）

- `POST /api/daily/generate`，body `{ report_date?: string }`（缺省取当天，
  Asia/Shanghai）。非流式，预算 60 秒；返回完整报告或业务错误码。
  幂等语义：同日重复生成即按当前档案与 mock 数据重算并覆盖。
- `GET /api/daily?date=YYYY-MM-DD`，读当日报告，无报告返回明确业务码。
- status → 信封：`ready` 与 `degraded` 均成功返回（`degraded` 带标记，前端
  按文档允许降级展示）；`data_insufficient`、`review_required`、
  `invalid_input` 各映射独立 ErrorCode，新增于 `app/common/codes.py`。
- 不接受前端提交手表指标或档案字段（信任边界在 16.8.8 第 1 条）。

## 6. 非协商约束对照

- 红旗与紧急情况不经过日报：`safety_context.review_required` 由后端按
  红旗结果与设备标记决定；工作流不内置生命体征告警，急诊路径不变。
- 模型输出不直接成用户文案：后端复核 status/结构/data_quality 后按板块
  落库与展示，`rendered_text` 仅作兜底纯文本，`degraded` 必须带标记。
- 密钥只经环境变量；mock 数据全部合成，测试夹具不含任何真实健康数据；
  `data_source=mock` 全链路保留，模拟记录不得混入真实档案或告警。
- 每条「联系疾病」必须能回查来源：落库 `used_record_ids`，展示层保留
  `source_refs` 板块。
