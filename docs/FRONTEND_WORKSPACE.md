# 清诉三页工作区

更新：2026-11-21。本文说明当前前端交互演示；真实医疗问答、OCR、数据库和通知接口尚未接入。

## 三个入口

| 页面 | 作用 | 主要操作 |
| --- | --- | --- |
| AI 对话 | 交互中心 | 新建问诊、恢复最近对话、从计划进入随访、核对并归档 |
| 健康档案 | 记录中心 | 按健康事件查看时间线，筛选来源，导入病历，安排随访 |
| 健康计划 | 任务中心 | 创建或暂停随访、开始或继续随访、录入本人医嘱、记录今日服药 |

桌面保留左侧导航、聊天和右侧上下文面板；手机使用底部三个入口，最近对话从顶部时钟按钮打开。纠偏前后对比和固定评分已从工作区移除。

## 路由

实际使用 uni-app 页面路由，同一套代码支持 H5 和微信小程序。

| 产品概念路径 | 当前页面路径 | 可选参数 |
| --- | --- | --- |
| 首页 | `/pages/index/index` | 无 |
| `/chat` | `/pages/chat/index` | `conversation_id` |
| `/health-records` | `/pages/health-records/index` | `record_id`、`mode=import` |
| `/health-plans` | `/pages/health-plans/index` | `tab=follow_up` 或 `tab=medication` |

H5 默认使用 hash 路由，例如 `/#/pages/health-plans/index`。三个工作区页面共用 `QWorkspace.vue`，问诊和随访共用输入、消息和上下文组件。

## 关联关系与状态

```text
PatientProfile
  ├── HealthEpisode：同一个健康问题或就诊过程
  │     ├── Conversation：consultation 或 follow_up
  │     ├── HealthRecord：ai_consultation / medical_document / ai_follow_up
  │     └── HealthPlan：follow_up 或 medication
  └── MedicationCheckIn：某计划、某日、某时刻的服用或跳过记录
```

字段定义以 `frontend/src/types/consultation.ts` 为准，当前 Pinia 实现在 `frontend/src/stores/consultation.ts`。

- 会话类型由创建入口明确指定，不根据用户的一句话猜测。最近对话混合展示两种类型。
- 新问诊独立开始；归档时建立健康事件。后续病历可选同一个事件，随访计划也关联该事件和来源记录。
- 咨询再次补充后允许重新归档，更新同一个记录 ID；原始对话仍可回看。
- 随访从计划启动，重复点击恢复同一个会话。至少有用户回复、等待演示回复完成并核对归档后，才标记计划和会话已完成。
- 已完成随访只读；新的不适通过新问诊记录，避免反复完成同一个任务。
- 医院病历单独保存原文转录字段，包括 `documentedDiagnosis` 和 `medicalInstructions`；不从聊天演示回复填入医生诊断。
- `confirmation=confirmed` 代表用户核对了记录或转录，不代表作出医疗诊断。`dataSource=demo` 标记预置虚构样例，`local` 表示本机录入。
- 用药按日期和提醒时刻生成今日操作，未到时间不可打卡；相同计划、日期、时刻只记一次。暂停或结束记录计划不会提供停药建议。

## 已实现与待接入

| 能力 | 当前实现 | 后续接入 |
| --- | --- | --- |
| 问诊与随访 | 统一 UI、明确模式、会话上下文、本地模拟回复 | 后端加载状态、AgentArts 分诊及随访、确定性校验后的文案 |
| 健康档案 | 时间线、来源筛选、详情、原对话引用、手动归档 | 用户身份、数据库、记录版本和服务端校验 |
| 病历导入 | 选择图片临时预览、手动填写或明确选择演示样例、转录核对 | 文件上传、原件存储、OCR、逐字段来源位置 |
| 随访计划 | 用户确认目标、时间和问题，启动对话，归档后完成 | AI 提议、服务端调度、授权通知和投递状态 |
| 用药计划 | 本人医嘱来源确认、起止日期和每日时刻、暂停/结束、当日打卡 | 服务端持久化、提醒发送、修改记录和设备同步 |

普通药品说明书不能代替个人处方或医嘱；当前不会通过说明书自动决定药物剂量、疗程和提醒时刻。AI 计划提议和 OCR 提取尚未接入，不会伪装成识别或发送成功。

后端只返回模型原文还不足以供前端展示，应继续遵守项目既有红旗、证据和文案出口规则。本次没有修改或移除这些后端约束。

## 本地数据

- 工作区状态存入 `clear-complaint.workspace.v2`，包括已提交记录、计划、对话和聊天输入草稿；没有账号或跨设备同步。
- 旧 `clear-complaint.demo-archive.v1` 会迁入统一档案，旧存储键保留。旧咨询记录不会被改标为医院确诊。
- 工作区数据格式异常或读取失败时，写入前必须先重新读取，并将非空原值备份到 `clear-complaint.workspace.v2.recovery.<id>`；读取或备份失败则不覆盖原值。
- 导入、计划表单未提交字段在本次打开应用期间跨页面保留，刷新后不保留；界面有对应提示。
- 病历图片仅在当前页面预览，归档只留文件名与手工核对文字，不能当作已上传的原始病历。
- 保存失败显示错误，内存内容保留，可重试本地保存；本机演示应使用虚构数据。
- 时间和今日打卡使用 `Asia/Shanghai`，不是随设备时区切换。

## 手动验收

1. 首页发送虚构症状，进入问诊；继续补充，核对归档，在健康档案看到记录及原对话入口。
2. 健康档案点“导入医院病历”，选择“填入演示样例”，核对确认后归档；测试不确认时不可保存。
3. 从记录安排未来随访或在健康计划新建计划；开始随访，确认聊天显示随访模式和目标。
4. 补充随访内容，归档并完成；档案新增随访来源记录，计划变成已完成，重复打开不再新增会话。
5. 用药计划确认本人医嘱后创建；验证已到时间的今日打卡、重复打卡、暂停和结束。页面不会发送真实通知。
6. 在不同对话间切换并恢复输入草稿；刷新后已提交记录仍存在；手机宽度检查底部导航和表单无横向溢出。

检查命令：`pnpm check:workspace`、`pnpm type-check`、`pnpm build:h5`、`pnpm build:mp-weixin`。工作区检查是独立 Node 脚本，复用已有 TypeScript/Vue 依赖，没有增加测试框架。
