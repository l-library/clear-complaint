# 病例集

20 例，九个病种域全覆盖。`pilot.jsonl` 是已填金标准的 4 例（P01–P04），`drafts.jsonl` 是待审的 16 例草稿（D01–D16，金标准为 `null`）。

## 审稿流程

```bash
cd experiment
uv run python -m tools.check_cases cases/drafts.jsonl      # 结构与变体一致性
uv run python -m tools.check_cases cases/pilot.jsonl --final   # 金标准齐全后
```

审稿时要看四件事，脚本只能替你查前两件：

1. **结构**：五变体齐全、V1 自带病程、V4 删掉病程、V2/V3 有归因或情绪标记、V5 有改写痕迹、V1/V4 不掺归因。
2. **长度**：V4 明显短于 V1。
3. **等价性（人工）**：把五段打乱顺序交给第三人，问「这五段说的是不是同一个人的同一件事」。答"不确定"的那条重写。
4. **金标准（人工）**：档位、首诊科室、应触发的红旗项。两人独立赋，不一致由第三人裁决。

## 档位判据（先统一，再标注）

| 档位 | 判据 |
| --- | --- |
| `emergency` | 命中任一红旗规则（见 `corpus/red_flags.json` 的 16 条） |
| `clinic` | 无红旗，但需要医生评估：做检查、需用药、症状持续加重 |
| `self_observe` | 无红旗，症状轻微且自限，一周内可复评 |

不先用这三行对齐，三个人会标出三套结果，裁决也没依据。

## 签核

仓库里不放签核文件。等价性确认与金标准裁决由团队在仓库外留档（含确认人、时间、裁决结果），需要时再整理进来。

仓库这边只保证一件事：**金标准不许和规则打架**。`check_cases` 会把每例的五个变体喂给红旗规则，如果金标准里某条红旗在五段文本里都命不中，就报出来——那说明要么触发词表缺了这种说法，要么这例不该标这条红旗。红旗漏检率是硬指标，这种错必须在跑矩阵之前就排掉。

## 红旗覆盖

急诊病例分布：P04（RF12 胸痛）、D01（RF06 持续高热）、D05（RF03/RF04 呼吸困难与发绀）、D06（RF09 少尿脱水）、D10（RF01 意识改变）。五条不同规则，不是同一条重复五次。

`coverage_probes.jsonl` 另存一批**少见说法**，不参与主指标，用来列「规则未覆盖表述清单」。写法故意绕开触发词，比如"胸这块别扭"而不是"胸口疼"。它们的作用是把红旗规则的边界摊开给人看，而不是好看的数字。

## 不做什么

- 不使用任何真实患者信息。全部为按指南描述构造的示例，`docs/stage1.md` 写明「示例性质、非临床验证」。
- 金标准不是临床判断，是三名工科生基于公开指南的合议结论，材料里必须原话写明。
